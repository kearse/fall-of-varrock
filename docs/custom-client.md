## 1. Why

We keep hitting walls that live inside the **client**, not the server or cache. The
server source (`Alter/`) and the game cache are fully ours, but the client we run —
**RSProx** (Blurite's RuneLite-based client for rev 228) — is a compiled app we don't
control. Some behaviors are baked into it and have no server/cache workaround.

Goal: eventually own a RuneLite-228 fork so the *whole stack* is ours — no surprise
client-side hijacks, ability to add custom packets, ship our own default plugins, and
brand it as ours.

Decision (2026-06-17): **start scoping now, keep using RSProx day-to-day, and keep a
running limitations log** (section 4). Fork work begins in earnest once the log shows
enough Tier-3 (client-only) blockers to justify the maintenance commitment.

## 3. The three tiers (where a problem gets fixed)

1. **Server-side** — command names, game logic, packets the server emits. Trivial.
2. **Cache edits** — interfaces, sprites, models, HUDs, minimap icons (displee / if3).
3. **Client fork** — client-side input handling, baked-in behaviors, custom packets,
   default plugins, branding. High cost (build + maintain + keep synced to cache rev).

A custom client is only *justified* by recurring **Tier-3** blockers with no Tier-1/2
workaround. The log below tracks exactly that.

  literal `::bank` we must **patch the gamepack** and **host our own**, then point
  `runelite_gamepack_url` at it. Two ways to patch:

     Smallest change; we host the patched jar locally and repoint the URL.
  2. **RuneLite injector + mixin** — the "proper" pipeline (inject a mixin into the
     gamepack at build time using the deob as the name map). Heavier setup.
- We already hold the **deobfuscated 228 client** at
  `~/.rsprox/launcher/repository/osrs-228-1.0.5.jar` — use it as the map to locate the
  scam-check method, then apply the patch to the obfuscated gamepack.

- `LofAlertsOverlay` (TOP_CENTER, pulsing red banner), `LofAlertsConfig` (toggles, text,
  duration, varp index).
- **Auto-discovery:** RuneLite's `PluginManager.loadCorePlugins()` does a runtime ClassGraph
  scan of the `net.runelite.client.plugins` package — so ANY plugin dropped in that package
  is picked up automatically; no registration/index file. Appears in the in-client Plugins
  config list (NOT the Plugin Hub — that's for externally-hosted community plugins).

**Server** (`game-plugins\...\content\war\SiegeAlertCommandPlugin.kt`): `::siegealert` toggles
`varp 5000` (the signal). The real War Brain can raise the same varp on raid start.

**Signal pattern (server→client, no custom packets):** server `player.setVarp(N, v)` → client
plugin reacts to `VarbitChanged` for varp N. **Gotcha:** N must be `< player.varps.maxVarps`
(= the cache's varp-definition count for the rev, NOT the client's `varp_count=15000`). Used
`5000`; the command bounds-checks. Varbit alternative needs a cache definition; raw varp doesn't.

## 5d. Migrated the siege HUD from cache interface → client overlay

The bottom-left siege bar was originally a **hand-authored cache interface** (group 1001,
the if3-byte-format HUD — see [[rsps-custom-interfaces]]) because we couldn't touch the
client. Now that we own the client, it's a **client overlay** instead — far simpler, no
cache authoring.

- **Server** (`content/war/WarHudPlugin.kt`): no longer opens interface 1001. Each refresh
  (~3s) it packs the war state into ONE varp **4601** (only sends on change):
  `bits0-1 phase | bits2-3 tier(0Probe/1Raid/2Siege/3unknown) | bits4-15 goblins | bits16-27 roster`.
  `::warhud` (admin) now just reports the state.
- **Client** (`net.runelite.client.plugins.warhud`, "Fall of Varrock War HUD", on by default): overlay
  reads varp 4601 via `client.getVarpValue(4601)` each frame, unpacks, draws the BOTTOM_LEFT
  bar — green "AT PEACE" / orange "LUMBRIDGE: <TIER> — N goblins" + drain bar / red "FALLEN".
- **Why packed into one varp:** minimizes varp-collision risk (only 4600 alert + 4601 hud
  used, both confirmed-adjacent-to-working) and is a clean single signal. 12-bit goblin/roster
  fields cap at 4095 (rosters are ≤300, fine).
- Test states: `::warraid siege` → orange bar; `::warfall` → red; `::warreset` → green peace.

## 5e. GOTCHA — persisted varps re-fire on login (transient signals must pulse)

`VarpSerialisation.asDocument` **saves every non-zero varp** and reloads it on login →
RuneLite posts `VarbitChanged` for it during the login sync. So a varp used as a momentary
*event* signal (e.g. the siege-alert at 4600) left non-zero **re-fires on every login**.
Symptom seen: red "SIEGE INCOMING" banner on login while the HUD correctly showed peace.

Rules for server→client varp signals:
- **Momentary events (alerts):** server **pulses** the varp — `setVarp(N,1)` then
  `player.queue { wait(2); setVarp(N,0) }` — so it returns to 0 and never persists. The
  client fires only on the **rising edge** (`value != 0`); the banner is duration-timed
  client-side, so it ignores the reset-to-0 (don't force-hide on 0). Also `onLogin` clears
  the varp defensively.
- **Continuous state (HUDs):** a refresh timer keeps overwriting it (peace packs to 0, which
  isn't saved anyway), plus `onLogin { refreshHud() }` corrects any stale value immediately.

## 5f. `::bank` fixed via chat-input rewrite (not a gamepack patch)

The OSRS scam-check (`::bank` → "…something very silly!" public chat) lives in the
**obfuscated gamepack** — and we have NO deob map for it (the `osrs-228-1.0.5.jar` in
`~/.rsprox/...` is RSProx's *protocol* lib `net.rsprox.protocol.v228.*`, not a client deob;
the "silly" string is in the cache, not any jar). So patching the gamepack method blind
would be heavy RE.

**Client-side chat-hook rewrite FAILED:** tried rewriting `::bank`→`::pbank` in
`ChatInputManager` at both the `chatboxInput` (handleInput, string stack) AND `runeliteCommand`
(runCommand, CHATBOX_TYPED_TEXT varc) callbacks — neither stopped the troll. Conclusion: the
scam-check runs in the gamepack's **Java key/chat handler, UPSTREAM of every RuneLite
clientscript hook** (that's why `::tabreset` reaches the server but `::bank` is caught first).
Only a gamepack-bytecode patch could intercept client-side, and we have no deob map (osrs-228
jar = RSProx protocol lib, not a client deob), so that's heavy blind RE. (The two ineffective
`ChatInputManager` edits are harmless dead code in the deployed client; revert on next build.)

**ACTUAL FIX — server-side troll intercept (works, any client):** we proved via CHATTRACE
that the client SENDS the troll as a normal public-chat packet, so the server sees it. In
`game-server/.../message/handler/MessagePublicHandler.kt`: if the incoming public message ==
`"Hey, everyone, I just tried to do something very silly!"`, **suppress the broadcast** (no
embarrassing line for anyone, incl. the typer) and run `executeCommand(client, "pbank")` to
open the bank. Net: `::bank` opens the bank, no troll. Bonus: works on ANY client (even stock)
and shields real scam-victims. Caveat: the troll line is generic across scam words, so we
assume the common one (`::bank`); other scam-bait words would also open the bank.
